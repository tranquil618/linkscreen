# ADR-0001：技术栈与总体架构

- 状态：已接受
- 决策日期：2026-08-03
- 产品名称：灵犀副屏（LinkScreen）
- 目标平台：Windows 11 x64、HarmonyOS 6.1

## 1. 背景

本项目需要让 HarmonyOS NEXT 平板成为 Windows 的可交互副屏。系统不仅需要传输桌面视频，还需要把触摸、键盘和手写笔事件传回 Windows，并在后期通过虚拟显示驱动实现真正的扩展桌面。

这是一个跨平台、实时、包含系统驱动的项目。技术方案需要同时满足以下要求：

- 能以教学方式分阶段开发和验证。
- 视频链路具有较低延迟，并能利用硬件编解码。
- Windows 和 HarmonyOS 两端边界清晰、便于调试。
- 可以逐步从镜像原型演进到真正的扩展屏。
- 最终能够安装、签名、测试和发布。

## 2. 决策

采用“平台原生应用 + 原生媒体引擎 + 共享协议库”的总体架构。

```text
Windows 主机端
├─ WinUI 3 用户界面（C# / .NET 8）
├─ 原生媒体与网络引擎（C++20）
└─ IddCx 虚拟显示驱动（C++ / UMDF）
              │
              │ 局域网控制与视频协议
              │
HarmonyOS NEXT 平板端
├─ ArkUI 用户界面（ArkTS）
├─ AVCodec 硬件解码
└─ 原生接收与渲染模块（C++ NDK）
```

## 3. Windows 主机端

### 3.1 应用界面

使用 C#、.NET 8 和 WinUI 3 实现：

- 设备发现和配对界面；
- 连接状态与性能信息；
- 分辨率、帧率、码率和画质设置；
- 日志、诊断和更新入口。

选择 C# 是为了降低桌面 UI 和普通业务逻辑的开发成本，让界面代码与实时媒体代码保持隔离。

### 3.2 原生引擎

使用 C++20 和 CMake 实现：

- Direct3D 11 图像资源处理；
- Windows Graphics Capture 屏幕采集；
- Media Foundation H.264 硬件编码；
- 实时网络传输；
- 帧队列、缓冲区与性能统计；
- Windows 输入事件注入。

WinUI 应用通过受控的原生接口调用 C++ 引擎，避免将 C++ 对象、异常或所有权规则直接泄漏到 UI 层。

### 3.3 虚拟显示驱动

使用 Windows Driver Kit、UMDF 和 IddCx 开发虚拟显示驱动。驱动负责：

- 向 Windows 报告虚拟显示器的连接和断开；
- 提供受支持的分辨率和刷新率；
- 接收 Windows 为虚拟显示器生成的帧；
- 将帧交给主机端媒体引擎。

驱动在镜像链路稳定后开发，以免在项目初期同时承担跨端媒体和驱动调试风险。

## 4. HarmonyOS NEXT 客户端

### 4.1 应用界面

使用 ArkTS 和 ArkUI 实现：

- 局域网电脑列表；
- 配对和连接流程；
- 全屏副屏页面；
- 画质、触控和显示设置；
- 权限、错误和重连提示。

### 4.2 原生媒体模块

使用 HarmonyOS NDK C++ 实现性能敏感部分，并通过 Node-API 向 ArkTS 暴露小型、稳定的接口。模块负责：

- 接收和重组视频数据包；
- 管理视频缓冲区和解码输入；
- 调用 AVCodec 进行 H.264 硬件解码；
- 将解码结果输出到 NativeWindow/Surface；
- 收集延迟、丢包率和帧率数据。

ArkTS 负责界面和状态管理，不在 UI 线程中执行视频数据处理。

## 5. 共享协议库

使用可跨 Windows 和 HarmonyOS 编译的 C++ 库定义 LinkScreen 协议。共享内容包括：

- 协议版本和能力协商；
- 消息头与序列化规则；
- 配对、认证和心跳消息；
- 视频帧分片信息；
- 触控、键盘和手写笔事件；
- 错误码和断线原因。

协议必须显式声明版本，并对未知消息保持向前兼容。禁止直接发送编译器内存结构，避免字节对齐、大小端和版本差异导致兼容问题。

## 6. 网络方案

### 6.1 设备发现

使用 mDNS 在局域网内发现 Windows 主机。用户也可以在自动发现失败时手动输入地址。

### 6.2 控制通道

控制通道采用可靠、有序的加密连接，承载：

- 配对和身份认证；
- 能力与显示参数协商；
- 触控和键盘事件；
- 心跳、错误和状态通知；
- 请求关键帧和动态调整码率。

原型阶段先验证可靠 TCP 消息通道；进入发布阶段前加入认证和传输加密。

### 6.3 视频通道

视频数据使用 UDP 传输，数据包包含会话标识、帧编号、分片编号、时间戳和载荷长度。

视频链路优先保证实时性。当数据已经过期时，不为等待完整旧帧而阻塞新帧。后续根据测试结果增加拥塞控制、动态码率、有限重传或前向纠错。

## 7. 视频方案

第一阶段使用以下基线：

- 编码格式：H.264；
- 分辨率：1920 × 1080；
- 帧率：30 fps；
- 初始码率：约 8 Mbps；
- 编码模式：低延迟；
- B 帧：关闭；
- 关键帧间隔：1 至 2 秒；
- 局域网端到端延迟目标：50 至 100 ms。

基本视频路径：

```text
Windows Graphics Capture / IddCx
              ↓
        Direct3D 11 纹理
              ↓
   Media Foundation H.264 编码
              ↓
          UDP 传输
              ↓
    HarmonyOS AVCodec 解码
              ↓
      NativeWindow / Surface
```

60 fps、H.265、HDR、音频和弱网增强不作为第一阶段要求，待基线链路稳定后分别评估。

## 8. 输入回传

HarmonyOS 客户端将本地输入转换为平台无关事件：

- 单指点击与拖动；
- 双指滚动；
- 鼠标移动和按键；
- 键盘按键与文本输入；
- 后续加入手写笔位置、压力和倾斜角。

事件携带归一化坐标以及画面方向、显示区域信息。Windows 主机根据虚拟显示器在桌面中的位置完成最终坐标映射，再通过受支持的 Windows 输入接口注入。

计划采用以下单仓库结构：

## 10. 开发与验证原则

- 每个阶段都必须能独立编译和运行。
- 先定义接口和测试，再扩展复杂实现。
- UI 线程不进行阻塞网络或视频处理。
- 网络输入默认不可信，所有长度、类型和状态都要验证。
- 日志不得记录配对密钥、令牌或用户输入内容。
- 性能优化必须以测量结果为依据。
- 重要技术变化新增 ADR，保留原始决策历史。

开发顺序如下：

```text
能编译
→ 能发现设备
→ 能建立连接
→ 能交换测试消息
→ 能传输静态画面
→ 能实时显示
→ 能回传输入
→ 能创建扩展屏
→ 能安装、测试和发布
```

## 11. 考虑过的替代方案

### 全部使用 C++

优点是语言统一、系统 API 访问直接。缺点是 Windows UI 和 HarmonyOS UI 的开发与维护成本较高，不利于分阶段学习，因此不采用。

### 使用 Flutter 或 Web 技术构建所有界面

优点是部分 UI 代码可以复用。缺点是本项目的主要难点位于平台原生媒体、Surface、输入和驱动接口，跨平台 UI 框架并不能显著减少核心工作，还会增加桥接层，因此不作为基线方案。

### 第一版直接移植 WebRTC

WebRTC 已提供拥塞控制、安全和实时媒体能力，但在 HarmonyOS NEXT 上的完整移植、构建和硬件解码接入会增加早期复杂度。第一版采用可观察、可逐步实现的自定义传输链路；待基线完成后，再用实际数据评估是否切换或复用 WebRTC 组件。

### 第一阶段直接开发 IddCx 驱动

这会把驱动、视频编码、网络和鸿蒙解码四类问题叠加在一起。决定先通过普通屏幕采集验证端到端链路，之后替换帧来源并加入虚拟显示器。

## 12. 影响与代价

该方案会产生 C#、ArkTS 和 C++ 三种主要语言，构建系统也不完全统一。但它让每个平台使用成熟的原生能力，并将高性能代码集中在边界明确的 C++ 模块中。

项目必须特别重视跨语言接口、线程生命周期、资源所有权、协议兼容和真机性能测试。换取的收益是更好的可维护性、原生体验以及演进为可发布产品的空间。
